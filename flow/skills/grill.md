# grill — 澄清意图

> 抄自:mattpocock/skills 的 `grilling`(对齐工艺)+ trellis 的 Evidence Rule + superpowers 的"批准前禁实现"硬门禁。
> 对抗的失败模式:agent 拿到模糊需求直接开写;为跳过提问找"合理化借口"。

## 何时用
需求不是"一句话就能无歧义执行"时。改文案这类明确小活可跳过(走 light 档)。

## 铁律
1. **一次只问一个问题**,不要一口气抛一串。
2. **每个问题附上你的推荐答案**("我倾向 A,因为…,你确认还是改?")——让用户确认比开放问答快一个量级。
3. **Evidence Rule:能查代码库回答的,绝不拿去问用户。** 先读代码,读不出来才问。
4. **按依赖顺序问**:先问决定其他问题的那个(架构 → 细节)。
5. **共识达成前,禁止写任何实现代码。** 这是硬门禁。

## 步骤
1. 通读现有代码 / 相关文件,列出你**已经能确定**的和**必须问人**的。
2. 逐个提问(遵守上面铁律),把答案就地记下。
3. 达成共识后,复述一遍最终理解让用户确认。
4. 用户确认 → 写批准标记:
   ```bash
   mkdir -p .flow && printf '%s\n' "$(date -u +%FT%TZ) approved: <一句话决议>" >> .flow/approved
   ```
   **没有这个标记,implement skill 会拒绝开工。**

## 交接
产出:`.flow/approved`(批准信号)+ 讨论共识。下一步交给 `spec`。
